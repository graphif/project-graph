# 图结构笔记与思维导图设计参考

整理日期：2026-09-29。

论文原始 PDF 归档见 [papers/ 下载索引](../../references/papers/README.md)，包含本地文件、来源、版本与尚未获取的条目。

本目录用于积累产品方法论、论文及 Project Graph 的发展建议。本文件整理自本次公开资料调研；产品能力以链接文档为准，后续可能变化。论文结论与项目设计推断分别列出，建议不代表已经实现或已经确定的开发计划。

项目背景依据：[基础思维导图画布](canvas-mvp.md)、[功能规划](TODO.md)。本次未通过源码或运行验证确认功能现状。

## 1. 建议定位

让零散想法逐渐形成可复用、可追溯知识的空间工作台。

思维导图提供快速输入和层级展开，图结构表达复杂关系，画布支持空间整理。核心使用流程是：围绕问题收集材料，自由摆放和分组，明确观点与关系，追溯证据，再把知识复用于其他项目。

## 2. 产品路线与方法论

| 路线 | 参考产品与资料 | 方法论 | 对本项目的启发 |
| --- | --- | --- | --- |
| 层级思维导图 | [Xmind Relationship](https://xmind.com/user-guide/relationship-new) | 以主题层级展开，用额外关系连接不同分支 | 保留快速生长，区分子主题与普通关联 |
| 链接式笔记 | [Obsidian Graph](https://obsidian.md/help/plugins/graph)、[Logseq 文档](https://docs.logseq.com/) | 页面或块引用逐渐积累知识网络 | 优先稳定引用、反向链接和局部邻域 |
| 空间知识整理 | [Heptabase 基本元素](https://wiki.heptabase.com/fundamental-elements)、[Obsidian Canvas](https://obsidian.md/help/plugins/canvas) | 通过位置、分组和连接组织材料 | 支持已有知识进入画布，以及临时想法沉淀为知识 |
| 结构化笔记 | [Tana 节点与引用](https://outliner.tana.inc/learn/features/nodes-and-references)、[Supertags](https://outliner.tana.inc/learn/features/supertags) | 对象可重复引用，并通过类型和字段组织 | 同一知识对象可在不同场景出现，正文保持一致 |
| 概念图 | [IHMC 概念图方法论](https://cmap.ihmc.us/docs/theory-of-concept-maps) | 围绕焦点问题，用连接词组成命题 | 让关系含义成为内容，而不只是连线外观 |

一个值得研究的边界：Obsidian Canvas 的纯文本卡片不会进入反向链接，需要先转换为文件。Project Graph 应明确临时画布内容成为长期引用对象的流程，而不是让用户事后处理大量副本。该产品行为见上述 Canvas 官方文档。

## 3. 论文阅读清单

### 空间整理与渐进结构化

- Marshall、Shipman，1993：[Searching for the Missing Link: Discovering Implicit Structure in Spatial Hypertext](https://people.engr.tamu.edu/shipman/viki/papers/ht93/ht93.html)。讨论通过空间排列表达隐含结构。设计启发：允许先摆放、聚集，再命名分组与关系；空间接近不自动等于语义关系。
- [VIKI/VKAT 论文索引](https://people.engr.tamu.edu/shipman/viki/papers/vkat-papers.html)，包含 1994 年的 *VIKI: Spatial Hypertext Supporting Emergent Structure*。可继续研究从自由排列到明确结构的交互。
- Hinckley 等，2007：[InkSeine: In Situ Search for Active Note Taking](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/chi2007-inkseine.pdf)。研究将搜索与材料收集融入笔记活动。设计启发：从当前节点检索，并将结果带着出处放回画布。

### 概念表达与学习

- Novak、Cañas，2008：[The Theory Underlying Concept Maps and How to Construct and Use Them](https://cmap.ihmc.us/docs/theory-of-concept-maps)。技术报告，强调概念、连接词、命题和焦点问题。设计启发：画布有待回答的问题，边能表达依赖、支持、反驳等含义。
- Nesbit、Adesope，2006：[Learning With Concept and Knowledge Maps: A Meta-Analysis](https://journals.sagepub.com/doi/abs/10.3102/00346543076003413)。汇总概念图与知识图的学习研究。设计启发：通过理解、回忆和迁移任务评价功能，不能根据画面丰富程度推断学习收益。

### 图表示与复杂度管理

- Okoe 等，2017：[Revisited Experimental Comparison of Node-Link and Matrix Representations](https://arxiv.org/abs/1709.00293)。比较节点连线图与邻接矩阵的任务表现。设计启发：图表示需要适配任务，不能假定全局连线图适合所有规模和问题；具体实现可先提供局部图和列表。
- 2023：[Sensecape: Enabling Multilevel Exploration and Sensemaking with Large Language Models](https://arxiv.org/abs/2305.11483)。通过多层抽象支持探索和知识组织。设计启发：容器增加摘要、展开和层级导航，让用户切换理解层次。

### AI 辅助与证据追溯

- 2023：[Graphologue: Exploring Large Language Model Responses with Interactive Diagrams](https://arxiv.org/abs/2305.11473)。将大模型回答转成可交互图。设计启发：围绕选中节点继续探索，生成结果应可检查和修改。
- 2025，2026 年修订：[ScholarMate: A Mixed-Initiative Tool for Qualitative Knowledge Work and Information Sensemaking](https://arxiv.org/abs/2504.14406)。结合非线性画布、文本片段、主题建议及来源追溯；页面标注被 CHIWORK '25 接收。设计启发：AI 辅助整理时保留原始证据，由用户控制分组与命名。

### 数据持有与长期使用

- Kleppmann 等，2019：[Local-first Software: You Own Your Data, in Spite of the Cloud](https://www.inkandswitch.com/essay/local-first/)。讨论离线工作、协作、长期保存与用户数据所有权。设计启发：优先可靠本地保存、迁移和开放导出；不据此直接决定引入协作框架。

证据边界：学习研究、方法论报告和交互系统研究回答的问题不同。原型研究能够支持设计探索，不足以直接证明本项目的长期生产力收益。本次属于定向资料调研，不是系统综述，也未逐篇复现或完整审查实验。

## 4. 建议的数据模型边界

以下是设计提案，不是当前代码结构说明。

| 概念 | 保存内容 | 示例 |
| --- | --- | --- |
| 知识对象 | 稳定 ID、标题、正文、来源、属性 | “空间记忆”笔记 |
| 语义关系 | 两端对象、关系类型、说明、证据 | 稳定布局有助于空间记忆 |
| 画布视图 | 当前问题、展示范围、布局方式 | 编辑器交互设计 |
| 对象呈现 | 对象引用、位置、尺寸、局部外观 | 同一笔记在两张画布中各出现一次 |
| 空间分组 | 当前视图中的包含与排列 | 待讨论区域 |

同一知识对象的正文共享，跨画布位置独立。需要明确区分删除呈现、删除引用关系和删除知识对象，避免连带丢失内容。

关系至少分为三类：

1. 空间包含：卡片放在哪个容器中。
2. 主题层级：哪个主题下面展开哪些子主题。
3. 语义关联：观点支持、反驳或依赖什么。

空间包含可继续采用单父约束；语义图允许多父与循环。同级主题生长只参考明确指定的主题层级，不把所有入边当作父主题。

现有画布文档提到同方向连线去重。引入语义关系后，同一对对象可能同时存在“引用”和“反驳”，去重规则需要考虑关系类型与用途。

这些边界不意味着必须引入图数据库。实现前应先评估已有存储、Godot 标准能力和社区库。本文不选择新依赖；引入时另行核实版本、哈希、许可证、平台和运行时兼容性。

## 5. 优先能力

### 5.1 有语义的边

先支持自由文字和少量常用关系，再扩展关系检索、过滤和证据。示例：自动布局“可能破坏”空间记忆，局部重排“用于缓解”布局变动。

### 5.2 从自由摆放到明确结构

支持“写碎片 → 拖到一起 → 分组 → 命名 → 摘要 → 明确关系 → 复用”的连续流程。系统可以提出分组建议，但不能仅因位置靠近便写入语义关系。

### 5.3 稳定布局与多层阅读

新对象局部避让，已有布局尽量稳定；支持固定位置和选区重排。容器折叠后展示摘要，并保留跨容器关系的可发现性。缩放可逐步呈现主题、标题和正文。物理反馈应服务于编辑，避免持续移动破坏阅读定位。

### 5.4 围绕问题查看局部图

| 用户问题 | 图能力 |
| --- | --- |
| 观点有哪些依据？ | 按关系类型遍历入边 |
| 修改方案会影响什么？ | 遍历依赖关系 |
| 两个主题如何联系？ | 在指定关系范围内搜索路径 |
| 哪些材料尚未整理？ | 查询缺少指定关系或归属的对象 |
| 哪些观点互相冲突？ | 查询显式反驳、冲突关系 |

路径存在不等于逻辑成立，连接数量不等于知识重要性。结果需要同时展示关系含义与出处。

### 5.5 来源和知识复用

优先节点详情、来源链接、原文摘录和稳定引用，再逐步支持 PDF、图片等附件。用户应能从结论返回材料，并查看材料被哪些结论使用。

## 6. 建议发展顺序

| 阶段 | 内容 | 用户价值 |
| --- | --- | --- |
| 数据可靠 | 格式兼容、未知对象保护、保存恢复、备份 | 敢于放入真实材料 |
| 表达理解 | 边文字、详情、来源、关系搜索 | 说明观点及其依据 |
| 管理复杂度 | 折叠、摘要、锁定、局部图、局部布局 | 材料增加后仍能读懂 |
| 长期复用 | 对象与呈现分离、跨画布引用、多视图 | 持续积累知识 |
| 辅助整理 | AI 建议分组、关系和摘要，预览后应用 | 降低整理成本，保留人的判断 |

对象身份与呈现边界应尽早设计，完整跨画布功能可以后续交付。AI 结果作为可检查提案，应用时进入一次可撤销事务。开发用 Godot MCP 不代表产品已经具备 AI 能力。

## 7. 后续手动验证方案

本方案尚未执行，涉及提案功能的步骤须在实现后验证。

目标任务：围绕一个问题整理十几份材料，形成有出处的观点图，再把其中知识复用于另一个项目。

1. 创建问题画布，录入材料、摘录和个人观点。观察是否能快速输入，无需预先决定全部分类。
2. 自由摆放、分组，再补充语义关系。观察是否能明确解释每条关系，并从结论回到来源。
3. 折叠、展开并执行局部布局。观察摘要、跨组关系和已有空间定位是否保留。
4. 将同一知识对象放入另一画布，修改正文。观察正文一致、布局独立；移除一个呈现不应误删原知识。
5. 保存重开，几天后重新阅读。观察能否找回结论、证据与未解决问题。

失败时重点检查：整理布局耗时过多、边含义不清、引用变成副本、折叠丢失上下文、删除呈现误删知识、保存后关系或来源丢失。

建议记录找到证据所需时间、重复录入量、重新理解旧画布所需时间及操作错误；不要只统计节点数量。
