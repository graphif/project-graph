# Project Graph CLI + Skills AI 接入方案

日期：2026-11-07
状态：已实现首版，持续验证中

## 1. 架构决策

提供 CLI 和 Skills，让外部 AI Agent 调用 CLI，CLI 通过本地 IPC 调用 GUI，由 GUI 统一打开、操作和保存工程。

```text
用户 ↔ 外部 AI Agent ← Project Graph Skill
                ↓
           Project Graph CLI
                ↓ 本地 IPC
           Project Graph GUI
                ↓
      工程实例 / 核心工具 / 历史 / 保存
                ↓
         结构化结果经 CLI 返回 Agent
```

CLI 是唯一自动化入口，GUI 是唯一工程运行时。CLI 不直接读取工程内容后修改或保存文件；路径检查、实例发现和安装定位不受此限制。

CLI 使用纯 Go 实现，独立于 MyGo GUI 入口。CLI 自身不初始化 MyGo、WebView 或前端运行时，也不依赖 Bun/Node.js。执行工程操作时连接 GUI；只有 GUI 未运行时才启动独立的 GUI 进程。GUI 继续使用 MyGo，工程业务继续在前端执行。

外部 Agent 负责模型、会话、任务规划和工具调用展示。GUI 只负责正常编辑体验和画布状态，不增加聊天窗口或工具调用记录面板。

选择 CLI 的依据是复用现有能力、减少协议和运行环境的维护成本，不依赖对 MCP 生命周期的判断。本方案不提供 MCP Server，并移除应用现有 MCP 客户端。

## 2. 目标与范围

### 2.1 必须实现

- 移除应用内 AI 对话及其模型调用基础设施。
- 保留并整理通用工具执行层，所有自动化修改在 GUI 当前工程实例中执行。
- CLI 自动连接 GUI；GUI 未运行时自动启动并等待就绪。
- 目标工程未打开时自动打开，成功后显示 toast。
- 已打开工程复用其当前内存状态，包括用户尚未保存的编辑。
- 同一工程的 CLI 请求按序执行，并与保存、关闭和另存为协调。
- CLI 返回稳定的结构化结果，明确修改是否应用、保存是否成功。
- 提供外部 Agent 使用的基础 Skill，以及 Windows CLI 路径定位脚本。
- 桌面和 Linux 虚拟显示环境采用同一执行路径。

### 2.2 本次不建设

- 应用内模型配置、对话、Agent 编排或 Skill 执行器。
- MCP 接入层、无 GUI 的工程读写运行时。
- GUI 工具调用记录面板。
- 跨命令、跨用户编辑的整段 AI 任务事务。
- 自动安装外部 Agent，或向其配置目录静默写入文件。

本文档同时记录已经落地的首版实现和后续限制。当前实现已经提供纯 Go CLI、GUI 本地 IPC、外部 Agent Skill 与工具目录；应用内 AI 对话、应用内 MCP 和旧 TypeScript CLI 已移除。

首版实现位置：

- `app/cmd/project-graph`：纯 Go CLI，提供工具发现、描述、调用和请求状态查询。
- `app/internal/automation`：版本化协议、客户端、工具目录和协议测试。
- `app/internal/desktop/automation.go`：GUI bridge、认证、就绪握手、请求去重与结果保留。
- `app/src/core/open-project-runtime-host.ts`：自动打开目标工程、按工程串行执行、修改后保存。
- `docs/agents/project-graph`：外部 Agent 使用的 Skill 和 Windows 定位脚本。

## 4. 职责划分

| 层             | 职责                                                             |
| -------------- | ---------------------------------------------------------------- |
| 外部 Agent     | 解释意图、调用模型、执行 CLI、向用户展示过程与错误               |
| Skill          | 定位 CLI、发现工具、指导工作步骤、说明失败处理                   |
| CLI            | 参数解析、路径解析、实例连接、必要时启动 GUI、发送请求、输出结果 |
| 桌面宿主       | 实例发现、本地通信、启动握手、工程所有权、系统文件能力           |
| GUI 工程运行时 | 工程打开、工具执行与排队、对象引用、历史、保存、生命周期         |
| 核心工具层     | 工具定义、输入校验、业务操作及明确的执行语义                     |

CLI 可以在本地完成版本、帮助和工具 Schema 查询，不因 `--help`、`--version`、`tool list/describe` 启动 GUI。目录和 Schema 来自同一套定义；执行前 GUI 必须再次校验，不能信任 CLI 已校验的输入。

### 4.1 Go CLI 与 GUI 的代码边界

建议新增 `app/cmd/project-graph/main.go` 作为独立 CLI 入口，并按需要将协议类型、连接与发现逻辑放到不依赖 MyGo 的内部包中。CLI 不导入 `app/internal/desktop`：当前该包包含 MyGo 事件和绑定，直接导入会把 GUI 依赖带回命令行程序。当前实现已把协议客户端放在 `app/internal/automation`，桌面桥接通过该纯 Go 包共享协议。

CLI 首版优先使用 Go 标准库处理命令、JSON、连接、超时及子进程，不为简单命令树引入新框架。Go 只实现协议客户端，不重写 TypeScript 的节点、连线、布局和序列化逻辑。

采用独立 CLI 可执行文件随应用分发，保留本文约定的 `project-graph` 命令路径。GUI 程序从配套安装布局定位；两个进程职责分开，避免执行 CLI 时进入 GUI 主函数、单实例窗口逻辑或图形初始化。

### 4.2 工具目录的单一来源

工具目录和输入 Schema 仍以 TypeScript 核心工具定义为唯一来源。通过发布资源生成步骤导出 JSON 目录，作为 Go CLI 的嵌入资源；Go 使用 `go:embed` 读取，因此离线查询工具不需要启动 MyGo 或 JavaScript 运行时。

导出器只依赖工具元数据，不加载 GUI 或业务执行器。目录包含版本和必要的能力、副作用说明；发布验证比较生成目录与源码定义，防止资源过期。此步骤属于后续发布集成，实施期间仍遵守禁止 Agent 运行 build 的约束。

Go CLI 本地校验命令语法及 JSON 格式；完整工具参数校验由 GUI 根据实际工具 Schema 完成，避免在 Go 中手写第二套参数约束。连接时校验目录/协议兼容性，不兼容则拒绝执行。

## 5. CLI 接口

### 5.1 保留的命令

```text
project-graph --help
project-graph --version
project-graph tool list
project-graph tool describe <tool>
project-graph tool invoke <tool> --project <path> --input <JSON>
```

`--project` 必须明确指定文件，避免错误操作当前活动标签页。相对路径基于 CLI 调用者工作目录解析，不能基于 GUI 的工作目录解析。

首版不因目标文件不存在就隐式创建空工程，返回 `PROJECT_NOT_FOUND`。自动打开与创建新工程是不同操作；需要新建时后续提供有明确契约的创建命令。

对于草稿，首版要求先保存为工程文件再通过路径操作。无需为草稿增加临时路径映射。

### 5.2 输出契约

调用类命令的 stdout 仅输出一个 JSON 结果。启动日志、依赖输出和诊断不得污染 stdout。`--help` 和 `--version` 继续使用文本输出。

建议调用成功结果为：

```json
{
  "ok": true,
  "requestId": "...",
  "projectPath": "...",
  "value": {},
  "state": { "applied": true, "persisted": true }
}
```

建议失败结果为：

```json
{
  "ok": false,
  "requestId": "...",
  "error": { "code": "PROJECT_SAVE_FAILED", "message": "..." },
  "state": { "applied": true, "persisted": false }
}
```

`applied` 表示本次工具是否已修改工程；`persisted` 表示本次调用要求持久化的状态是否已经保存。读取操作通常为 `applied: false`，但分配新对象引用时仍需等待相应引用持久化。无法确认时使用 `null`，不能返回虚假的 `false` 或成功。

退出码建议统一为：0 成功，1 运行失败，2 命令或输入错误，130 在提交修改前确认取消。失败 JSON 写 stdout，stderr 仅作补充诊断。此规则与现有 stderr 错误输出存在兼容变化，需要同步更新文档、测试和 Skill。

`tool list/describe` 保持机器可读，增加必要的副作用、前置条件和事务说明。目录中声明的能力、取消与原子性必须与实际执行器一致。

### 5.3 主要错误

| 场景                   | 建议错误码                                  | 处理                         |
| ---------------------- | ------------------------------------------- | ---------------------------- |
| 找不到 GUI 程序        | `GUI_EXECUTABLE_NOT_FOUND`                  | 修复安装或显式指定路径       |
| GUI 启动失败或未就绪   | `GUI_START_FAILED` / `GUI_READY_TIMEOUT`    | 返回原因，不退回直接读写工程 |
| CLI 与 GUI 不兼容      | `PROTOCOL_VERSION_MISMATCH`                 | 更新配套安装                 |
| 工程不存在或打开失败   | `PROJECT_NOT_FOUND` / `PROJECT_LOAD_FAILED` | 返回路径及可理解的原因       |
| 工程被不可连接实例持有 | `PROJECT_BUSY`                              | 保持所有权，不绕过锁         |
| 工程要求升级           | `PROJECT_UPGRADE_REQUIRED`                  | 显式授权后再升级             |
| 对象引用失效           | 沿用现有引用错误码                          | 重新读取对象，禁止猜测引用   |
| 已修改但保存失败       | `PROJECT_SAVE_FAILED`                       | 报告已应用，不重复执行修改   |
| 连接中断且结果无法确认 | `RESULT_UNKNOWN`                            | 查询请求状态，不自动重放     |

新旧工程版本升级继续沿用明确授权约束，例如现有 `--allow-upgrade`；不能让自动打开在后台等待不可见的交互对话框。

## 6. GUI 启动、发现与工程打开

### 6.1 实例发现和就绪

1. CLI 查找同一用户、同一安装或兼容通道的运行实例。
2. 已有工程持有者优先；否则连接默认 GUI 实例，请求打开工程。
3. 没有可用实例时，CLI 从自身安装布局定位 GUI 程序，以参数数组启动。
4. 等待宿主通信就绪、前端监听注册及工程服务可用；进程存在不代表已经就绪。
5. 握手检查协议版本，再提交请求。具体超时作为实现常量和可测试行为，不无限等待。

多个 CLI 同时冷启动时，复用应用单实例机制并汇合到同一就绪流程。现有第二实例处理会聚焦窗口，实施时要区分普通用户启动与 CLI 启动，避免每次自动化请求都抢焦点。

GUI 启动失败应保留原始诊断并返回给 Agent。CLI 退出后不关闭 GUI，后续调用继续复用。

### 6.2 打开工程

GUI 接到工程路径后：

1. 规范化路径并取得工程所有权；符号链接和路径别名应遵循现有规范化机制。
2. 已打开则复用当前实例；正在打开则等待同一个 Promise，避免重复标签页。
3. 未打开则走正常文件打开、解析、迁移检查和服务初始化流程。
4. 打开成功后显示一次 toast：“已通过 CLI 打开工程：文件名”。后续调用不重复提示。
5. 工程完全就绪后执行工具。

新打开工程正常显示为标签页；已经打开的工程不因后续命令反复切换标签页或窗口焦点。操作指定工程的选择和视野，不错误地使用另一个活动工程的状态。

自动打开失败返回 CLI 错误，前端异常按现有 ErrorHandler 约定处理，不能只 toast 后吞掉错误。

## 7. 本地通信与请求状态

优先复用现有桌面 Bridge 和本地转发协议，不为本方案引入远程 HTTP 服务或新的通用 RPC 框架。

请求至少携带协议版本、请求 ID、绝对工程路径、工具名和输入。取消和状态查询关联同一个请求 ID。

本地 IPC 仅接受当前用户的可信连接：使用具备用户权限限制的本地端点；如果继续采用 loopback TCP，则需要随机认证凭据、用户私有发现记录和回环监听约束。随机端口本身不构成认证。不得把令牌或敏感参数写入普通日志。

工具只允许调用目录中声明的名称和 Schema，不开放任意脚本执行接口。

### 7.1 请求去重与结果未知

- GUI 在内存中维护有界请求状态：排队、执行、成功、失败和确认取消。
- 同一请求 ID 和相同输入重复提交时返回已有状态或结果，不重复执行。
- 同一 ID 携带不同输入时拒绝。
- CLI 提供请求状态查询入口，建议命令为 `project-graph request status <request-id>`。
- CLI 允许显式传入请求 ID，用于超时后的关联查询；默认自动生成。具体参数需在实现时加入帮助和 Skill。
- GUI 重启后内存记录丢失，旧请求返回结果未知。首版不建设持久化请求账本，也不承诺跨崩溃 exactly-once。
- 断线不能等价于执行失败。状态未知时 Agent 应先查询，再检查工程实际内容，不自动重复创建或删除。

结果缓存按数量和时间限制；过期查询明确返回未知。CLI 超时不能隐式中止已经提交的修改。

## 8. 并发、历史与保存

### 8.1 操作顺序

复用现有 `OpenProjectRuntimeHost` 的按工程队列。首版同一工程的 CLI 读取和修改均排队，保证读取能看到前面已完成操作。不同工程可以独立执行。

单线程不等于没有竞态。异步工具等待文件或网络期间，用户仍可能编辑。执行器应先完成耗时准备，再重新校验引用和必要状态，最后以短暂同步步骤提交；依赖旧快照的操作可通过工程修订号检测冲突，不能覆盖期间用户的新修改。

不在整个异步任务期间锁住画布。需要跨异步边界改造的工具逐个核查，避免在校验后再次长时间等待才提交。

### 8.2 保存

- 已打开工程以当前内存状态为准，不重新加载磁盘覆盖用户修改。
- 修改类调用返回成功前，由 GUI 正常保存链路完成保存，并保存必要对象引用。
- 保存的是工程当时的整体状态，可能包含用户之前未保存的编辑；这项行为必须写入 CLI 文档和 Skill。
- 读取命令不主动保存无关的用户内容；如果生成新引用，只持久化引用所需状态。
- 保存串行化，防止较早快照晚于较新快照落盘。返回的持久化状态必须覆盖本次修改对应的修订。
- 保存失败保留 GUI 内存修改和脏状态，通知 GUI 用户，并向 CLI 返回明确状态；不自动重做工具。

### 8.3 历史、取消与生命周期

沿用工具真实的历史粒度，不承诺所有工具都已原子化，也不把整段 Agent 会话合并成一次撤销。非原子操作若部分完成，必须返回已完成范围和状态。

排队期间取消可以安全退出；执行中取消是协作式请求，不能把已应用修改报告为未执行。修改已经提交时，应完成必要保存或返回明确的未保存状态，保留正常撤销能力。

关闭和另存为与调用队列协调：关闭开始后拒绝新请求，等待正在提交或保存的操作结束；另存为后更新所有权及路由。使用旧路径的新请求不得静默修改另存为后的工程。

## 9. Skills 与安装路径

### 9.1 基础 Skill

提供一个可分发目录，推荐源目录为 `skills/project-graph/`：

```text
project-graph/
├── SKILL.md
└── scripts/
    └── find-project-graph.ps1
```

基础 Skill 包含：定位程序、工具发现、工程选择、对象引用使用、创建与布局顺序、结果校验、保存副作用，以及失败和结果未知时的处理。

工具参数以 `tool describe` 为准，不在 Skill 中复制全部 Schema。Skill 是外部 Agent 的说明文档，不由 Project Graph 加载或执行。领域 Skill 等有明确需求后再增加。

分发时提供目录和安装说明，让用户放入其外部 Agent 支持的位置；不同 Agent 的 Skills 目录不假定相同。发布与应用版本配套的 Skill，基础工作流应尽量使用稳定 CLI 接口。

### 9.2 路径规则

所有平台先检查用户显式设置的 `PROJECT_GRAPH_CLI`，它表示 CLI 可执行文件绝对路径。

| 平台    | 默认方式                                                 |
| ------- | -------------------------------------------------------- |
| Windows | 调用附带 PowerShell 定位脚本                             |
| macOS   | `/Applications/Project Graph.app/Contents/project-graph` |
| Linux   | `/usr/bin/project-graph`                                 |

macOS 和 Linux 路径是本方案采用的发布契约，实施时必须验证安装包实际满足，不将其写成已验证事实。

Windows 脚本按以下顺序定位：显式环境变量、PATH 中命令、安装器注册信息。具体注册表项及 CLI 相对位置以实际安装器为准，兼顾用户级和系统级安装及适用的注册表视图；不从卸载程序路径盲推 CLI 路径，不递归扫描磁盘。

显式设置无效时直接报错，不悄悄使用其他安装。便携版使用显式路径。PATH 需要能解析到真实可执行入口，排除同名目录、别名和无关脚本。

脚本成功时 stdout 只输出绝对路径，失败时 stderr 输出原因并返回非零码。使用 PowerShell 是为了依赖系统现有能力，不要求 Node.js 或 Python。不得修改系统执行策略来运行脚本；受策略限制时提供手动设置路径的方式。

Agent 必须以参数形式调用程序并正确引用含空格路径，禁止拼接后 `eval`。脚本只做路径定位，GUI 启动和工程打开统一由 CLI 实现。

## 10. 模型能力外移

移除模型配置时同步梳理隐藏依赖，不能只删除聊天 UI。

- 图片识别由外部 Agent 的视觉能力完成；CLI 提供受支持的图片导出或读取工具，返回绝对文件路径、MIME 类型等必要信息。
- 临时导出文件需有明确位置和有效期，不能在 Agent 尚未读取时立即删除。输出目录受调用者或应用私有目录约束。
- Agent 无法读取本地图片时返回能力限制，不让 GUI 偷偷恢复模型调用。
- 搜索或外部资料获取由外部 Agent 完成；现有图片搜索等联网工具逐项判断保留价值，不因位于 `ai-engine` 就全部删除。
- 文本生成、总结和结构推理由 Agent 完成，再使用通用节点、连线和布局工具落地。
- 保留稳定对象引用及其持久化，去掉名称和生命周期对 AI 会话的依赖。

## 11. Linux 服务器部署

服务器使用同一 GUI 程序和 IPC。通过 `xvfb-run` 等虚拟显示方式运行 GUI，CLI 连接该实例，不建设第二种工程执行环境。

部署要求：安装应用所需的 WebView/图形运行库、字体和虚拟显示依赖；GUI 与 CLI 使用同一用户、兼容版本及相同应用数据目录。不得把 IPC 暴露为公共网络接口。

推荐由服务管理器维持虚拟显示与 GUI 生命周期。CLI 自动启动 GUI 时继承部署环境中的显示配置；没有有效图形环境时返回明确启动错误。只在一个短暂命令外层执行 `xvfb-run` 并不能保证显示环境长期存活，应覆盖 GUI 的整个生命周期。

虚拟显示中的 toast 不要求有人观看。Agent 以 CLI 结果为准。

## 12. 代码整理与删除范围

建议将通用工具、执行器和引用组件归入 `app/src/core/automation/`，遵循 kebab-case。纯 Go CLI 入口位于 `app/cmd/project-graph/`，协议客户端放在不依赖 MyGo 的内部包中；原 `app/src/cli/` 的命令实现和独立运行时在迁移完成后移除，仅按需要保留工具目录导出等开发资源。优先复用已有文件，不引入多层空壳抽象。

迁移后移除或替换：

- `ai-window.tsx`、AI 专用入口、快捷键、子窗口注册和菜单项。
- 模型设置、Key、请求头、模型列表与上下文窗口查询。
- 会话存储、记忆压缩、请求追踪和 Agent 工具适配层。
- 应用内 MCP 配置、工具窗口、stdio 管理及 Go MCP 绑定。
- 内置 Skill 发现、激活和信任管理。
- CLI closed-project 运行时、为其模拟的 DOM/渲染/平台实现及专用打包资源。
- 不再被任何功能使用的依赖、测试、国际化文案和配置。

删除前逐项检查调用者。CLI 工具的图片工具窗口、通用网络工具或历史组件若仍有用途，应迁移保留。所有权 helper 是否仍需独立进程由现有实现依赖决定，不能与 closed-project 运行时一并盲删。

旧模型凭据和会话数据不再读取，不自动发送或导出到外部 Agent；是否清理历史数据另行决定，不在本次迁移中做破坏性删除。项目中的普通内容和附件必须保留。

删除设置、快捷键和 UI 时遵循对应仓库技能。国际化修改维护手写语言文件，不手改自动生成的 `zh_TW.yml`。

## 13. 实施阶段

### 阶段一：确定并补齐协议

- 固化 CLI 结果、错误、版本握手和保存语义。
- 实现独立 Go CLI 入口与无 MyGo 依赖的协议客户端，保留既有命令用法。
- 从 TypeScript 工具定义导出并嵌入 JSON 目录，确保工具发现无需启动 GUI。
- 为现有工具标注真实副作用和事务边界。
- 保留现有工程转发测试，补齐保存结果和状态测试。

完成条件：已打开工程能通过统一响应契约操作，成功与持久化含义可验证。

### 阶段二：自动启动与自动打开

- 复用宿主单实例和 Bridge，增加全局实例发现及就绪握手。
- GUI 未运行时启动，工程未打开时自动打开并 toast。
- 并发启动和并发打开汇合，保持路径路由和所有权。
- 补齐请求状态、去重及断线后的查询。

完成条件：从无进程、无已打开工程状态执行一条命令即可完成操作并保存。

### 阶段三：执行能力收敛

- 通用工具和对象引用迁出 AI 模块。
- 替换 CLI 独立工程执行分支，确保失败不回退直接文件修改。
- 图片等模型依赖外移，保留必要导出能力。
- 完善异步提交、关闭、另存为和保存协调。

完成条件：所有支持的 CLI 工具只在 GUI 执行，不再依赖模型配置或独立工程运行时。

### 阶段四：Skills 与移除旧入口

- 提供基础 Skill、Windows 定位脚本和安装说明。
- 删除内置 AI、MCP、Skills 运行时和未使用依赖。
- 更新 CLI 文档、发布资源与相关设置、快捷键和文案。

完成条件：干净安装后，外部 Agent 能依靠 Skill 完成读取、修改、布局和验证，应用不再包含旧 AI 入口。
